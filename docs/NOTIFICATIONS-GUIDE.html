1. Overview

Every notification goes through one function, notify() in src/lib/notify/dispatch.ts. It does four things and never throws, so a failed notification can't break the action that triggered it:

  1. In-app: writes a Notification row. It shows in the header bell (polls every 60s and on tab focus) and on /notifications. No setup needed.
  2. Browser push: sends a Firebase Cloud Messaging web push to every browser/device the user has enabled alerts on. Needs Firebase credentials (section 5); without them it silently does nothing.
  3. Email: sends through SMTP (nodemailer) when SMTP env vars are set. Otherwise it is skipped and, in development, the message is printed to the server console.
  4. Audit log: writes a NotificationLog row with the real status (SENT / FAILED / SKIPPED), visible on each user in Admin → Clients.

Pass email: false and/or push: false to skip a channel. Push follows the same rules as in-app: every row in the table in section 2 also pushes (the Email column does not apply to push).

2b. For creators (instructors & mentors)

Creators get notifications about their content, and admins get the matching review pings. Related lesson alerts are coalesced: while an admin hasn't read one, further "lessons awaiting review" in the same hour update that single row instead of adding more (and send no extra push/email).

The digest runs from /api/cron/creator-digest, scheduled in vercel.json for Mondays 07:00 UTC, and uses the same CRON_SECRET as the reminders cron. Test it locally with curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/creator-digest. Code: src/features/courses/server/notifyCreator.ts.

The notification view

  • Icons by type (trophy for milestones, graduation cap for enrolments, clipboard for reviews, and so on) in the bell and on the page. The mapping lives in kindMeta() in src/lib/notify/client.ts; add a rule there for any new kind.
  • Category tabs on /notifications (Learning, Reviews, Bookings, Events, Account, Announcements) with unread counts, plus an "Unread only" toggle.
  • Grouped by day: Today, Yesterday, Earlier this week, Older.
  • Dismiss a single item with the × button (DELETE /api/notifications?id=), or "Clear read" for all read items.

4. Email provider setup

Option A: Resend (recommended, simple)

  1. Sign up at resend.com, then Domains → add your domain and add the DNS records they show (SPF/DKIM).
  2. API Keys → create a key.
SMTP_HOST="smtp.resend.com"
SMTP_PORT="465"
SMTP_USER="resend"
SMTP_PASS="re_xxxxxxxxxxxx"
EMAIL_FROM="AI Bootcamp <no-reply@your-domain.com>"

Option B: Gmail (fast for testing)

Turn on 2-step verification, then create an App Password (Google Account → Security → App passwords).

SMTP_HOST="smtp.gmail.com"
SMTP_PORT="587"
SMTP_USER="you@gmail.com"
SMTP_PASS="xxxx xxxx xxxx xxxx"
EMAIL_FROM="AI Bootcamp <you@gmail.com>"

Option C: SendGrid / Postmark / SES

Any SMTP relay works. SendGrid uses SMTP_USER="apikey" and the API key as SMTP_PASS.

Libraries: email uses the existing nodemailer, WhatsApp uses fetch to Twilio. Browser push added two packages: firebase (browser SDK, loaded only when a user turns alerts on) and firebase-admin (server sender).

5. Browser push (Firebase Cloud Messaging)

How it works. A signed-in user clicks Turn on browser alerts at the bottom of the bell dropdown. The browser asks permission, Firebase issues a token for that browser, and POST /api/notifications/push stores it in PushToken. From then on every notify() also calls FCM for that user's tokens. The service worker public/firebase-messaging-sw.js shows the notification (even when the site is closed) and opens the link on click. If the tab is open, the bell refreshes instantly. Dead tokens are deleted automatically when FCM rejects them. The toggle link is hidden until the Firebase variables are set.

One-time Firebase setup (free, Spark plan)

  1. Go to console.firebase.google.com → Add project (Analytics not needed).
  2. Project settings → General → Your apps → Web (</>) → register an app. Copy apiKey, authDomain, projectId, messagingSenderId, appId into the matching NEXT_PUBLIC_FIREBASE_* variables.
  3. Project settings → Cloud Messaging → Web Push certificates → Generate key pair. Copy the public key into NEXT_PUBLIC_FIREBASE_VAPID_KEY.
  4. Project settings → Service accounts → Generate new private key. Open the downloaded JSON, remove the line breaks so it is one line (for example jq -c . key.json), and paste it as FIREBASE_SERVICE_ACCOUNT_JSON='...' (single quotes in .env.local). Delete the downloaded file afterwards.
  5. On Vercel add the same variables under Project → Settings → Environment Variables and redeploy.
  6. If the console says the Firebase Cloud Messaging API (V1) is disabled, enable it (Cloud Messaging tab). The legacy server key is not used.

Test it

  1. Restart npm run dev, open http://localhost:3000 (localhost counts as secure; any other host needs HTTPS), sign in, click the bell → Turn on browser alerts → Allow.
  2. As an admin send an announcement to that user's role. You should get an OS notification within a few seconds, even if you switch to another tab or minimise the browser.
  3. On Android: open the deployed HTTPS site in Chrome, enable alerts the same way. Installing it to the home screen is optional on Android.
  4. Admin → Clients → user shows a PUSH row in the delivery log (only written when a device was actually attempted).

Push limitations

  • iOS Safari only supports web push after the site is added to the home screen (iOS 16.4+). Not supported in other iOS in-app browsers.
  • Needs HTTPS in production, and the user must grant permission. If they block it, they must re-allow it in browser site settings (the bell shows a hint).
  • Tokens are per browser profile. A user with a phone and laptop registers both and gets both.
  • Tokens live in the database, so the Vercel /tmp SQLite caveat in section 10 applies: registrations are lost when the serverless instance recycles.
  • Push is not queued or retried by us; for large broadcasts consider a background job later.
  • This is web push only. A native Android app would need an app wrapper (Capacitor/TWA) and the same Firebase project, plus google-services.json.
  • Check Firebase's current free-tier terms; FCM messaging has historically had no per-message charge.

6. WhatsApp (optional)

  1. Create a Twilio account → Messaging → Try WhatsApp (sandbox) to test. Recipients must join the sandbox first.
  2. For production, get a WhatsApp sender approved and register message templates. WhatsApp blocks free-form business-initiated messages outside a 24-hour window.
  3. Set the three TWILIO_* variables.

7. Cron / reminders

vercel.json runs /api/cron/reminders daily at 06:00 UTC (and /api/cron/creator-digest weekly, section 2b). It reminds confirmed bookings starting in the next 36 hours, once each. Set CRON_SECRET in Vercel. Test locally:

curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/reminders

8. How to test

  1. npm run dev, sign in as an admin, open Dashboard → Admin → Announcements, pick "Learners", send.
  2. Sign in as a learner in another browser: the bell shows a badge within 60 seconds (or on tab focus). Click the item to mark it read and follow its link.
  3. With no SMTP configured, the server console prints [email:dev-preview] and the log shows SKIPPED. That's expected.
  4. Other quick checks: register a new instructor (admins get a notice), approve them in Admin → Faculty (they get a notice), change a role as super admin, enrol in a course.

I ran these checks against a local server: broadcast as admin delivered 3 inbox items and 3 honest SKIPPED email logs, a learner calling broadcast got 403, an admin couldn't mark a learner's notification read, and mark-read dropped the unread count to 0.

10. Known limitations

  • Vercel + SQLite: src/lib/prisma.ts copies the DB to /tmp on Vercel, so writes (including notifications) are ephemeral per serverless instance. In-app notifications won't reliably persist there until you move to a hosted database (Postgres/Turso). scripts/startup.postgres.sh hints you've considered it.
  • The committed prisma/dev.db now includes the new Notification and PushToken tables. On any other database run npx prisma db push.
  • The in-app bell polls every 60s (instant only when push is on and the tab is open).
  • Email isn't queued: it is sent inline, with 10 recipients at a time for broadcasts. For thousands of users, move broadcasts to a background queue.
  • No per-user preferences yet (users can't mute email).
  • Event start reminders (like booking reminders) are not implemented.
  • Event-interest notices to hosts are type-checked but I had no upcoming approved event in the dev DB to exercise them end to end.
  • prisma format realigned some whitespace in schema.prisma. That is cosmetic.
